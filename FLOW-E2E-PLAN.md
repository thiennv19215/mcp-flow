# Flow end-to-end rollout

This plan follows the live route used by this repository: MCP client → local forwarding owner → authenticated remote device session → VPS queue → browser extension → Flow tab → Chrome download → MCP-visible file. TobyFlow is a reference for Flow-specific driver isolation, preflight gates, positive submit evidence, operation checkpoints, normalized errors, and retrying only when an operation is known to be safe. Its page selectors and internal API paths are not copied as dependencies.

## Phase 0 — Freeze the contract and establish evidence

- Record MCP tool arguments, backend methods, extension capabilities, output fields, and the expected owner of each filesystem path.
- Keep local unit tests, local HTTP/MCP E2E, extension transport E2E, and real Flow acceptance as separate evidence levels.
- Gate: every implemented tool has a known route and a test boundary; no test reports a real Flow pass when it used a fake backend.

## Phase 1 — Session and connection recovery

- Verify pairing, device identity, bearer-token isolation, session replacement, stale-session rejection, websocket and HTTP-poll reconnect, and the local owner’s forwarding route.
- Verify that status reports the same device, remote backend, extension version/capabilities, job list, and usable output location.
- Gate: MCP status and a harmless read-only tool work after reconnect and reject the wrong device token.

## Phase 2 — Input files and generation submission

- Stage local MCP files into the authenticated per-device VPS upload area before forwarding calls that use first/last frames, image references, character images, media upload, re-angle inputs, or explicit assembly tracks.
- Verify model capability checks, settings, references, frames, and local/asset/character input distinctions before queueing.
- Verify submit confirmation using editor clearing, disabled/accepted controls, or a new Flow tile; never replay a possibly submitted paid job.
- Gate: image and video request payloads arrive intact at the intended device queue; invalid combinations fail before submission.

## Phase 3 — Job lifecycle and classified recovery

- Exercise queue persistence, wait/task IDs, progress, cancel-before-start, safe retry, restart during queued/running work, quota, rate limit, expired session, generation failure, captcha, and download failure.
- Keep unknown submission outcomes blocked from automatic retry. Keep captcha and account verification as a manual checkpoint.
- Gate: each terminal state is represented consistently in MCP and Studio; only confirmed safe failures can be retried.

## Phase 4 — Flow library operations

- Exercise projects/open-project, asset and character listing, reference attachment, upload, download, rename/trash, character create/edit, edit, continue, agent batches, and re-angle.
- Check that every destructive or paid operation has the intended confirmation and that partial batch failures preserve completed items.
- Gate: each operation is covered by a local fake-extension E2E before live acceptance.

## Phase 5 — Output and local workflows

- Transfer browser-owned download bytes back to the VPS output directory, then materialize authenticated remote outputs onto the MCP host with size/checksum/path checks.
- Exercise narration, voice listing, assembly with returned or explicit tracks, output listing, and local discard semantics.
- Gate: returned file paths exist on the MCP host and can be consumed by a subsequent MCP tool.

## Phase 6 — Live acceptance

- Run status and library reads, then one user-authorized image and one video after Flow is ready.
- Verify the job lifecycle, resulting bytes, local output paths, asset listing, and one reuse path such as download or assembly.
- Gate: record real Flow evidence separately from all automated/fake tests. Pause for user verification if Flow presents CAPTCHA or account review; do not automate or bypass it.

### Local API audit runner

`node scripts/audit-native.mjs` defaults to `--mode readonly`: it reads status, projects, assets and characters from the local Flow API and writes a timestamped diagnostic report. It does not open a project or submit a job. The runner defaults to `http://127.0.0.1:18897`; an override may use only `http://127.0.0.1:<port>`, `http://localhost:<port>`, or `http://[::1]:<port>` via `FLOW_LOCAL_API_BASE`. Any remote host, including the VPS, is refused before the token is read or an API call is made.

Each runnable generation mode submits at most one queue job with `submit_only: true`, zero retries and one variant (Agent mode sends one prompt). The runner polls only until correlated `request_dispatched` or `status: submitted` evidence appears; it never waits for a rendered image/video and never replays a job if dispatch is unknown. Live video and frame probes are capped at 15 credits; live text-to-image is capped at zero. The video-reference route currently fails before queueing, so no live video-reference probe is available. If transport is implemented later, it must retain the 15-credit cap. Do not use `allow_unknown_quote` in live acceptance: stop before dispatch when Flow does not show a verifiable quote within the mode's cap. Edit and continue remain unrun until their quote/confirmation path meets that gate. Character mode requires complete character-list snapshots with stable UUIDs before and after create: it refuses an existing requested name, then accepts success only if exactly one new UUID has the exact requested name and all baseline UUIDs remain. The list endpoint includes optional `uuid` values only from character-specific identity attributes; detailed status exposes `characterListDiagnostics.scanComplete` and `stableUuidCount`. If the extension cannot prove completion or any row lacks a stable UUID, the runner fails before creating anything. Character creation is a library operation, not a queued `submit_only` job. Upload is also a direct library operation, not a generation job.

Before a submit, the extension checks the main-world observer. If Flow has replaced its XHR/fetch hooks and there is no active correlation attempt, it reinjects the observer once and reads health again. The observer's own active-attempt guard prevents replacing a live correlation; if the one repair does not restore readiness, the operation stops before sending anything. This does not retry or replay a generation request.

The schema exposes `reference_images` as image paths/assets/characters, so the runner includes image references for image and video generation. A distinct `video_reference` shape now accepts an exact video asset title and integer `start_frame_index` / `end_frame_index`, with validation for video-only use, a valid range, and conflicts with image references or first/last frames. The API deliberately fails closed with `FLOW_VIDEO_REFERENCE_CONFIG_UNAVAILABLE` before queueing: this shape does not yet submit a request and is not an E2E pass. The schema supports one or two video frame inputs; the pair mode checks both start and end frames in one video request.

```powershell
node scripts/audit-native.mjs --mode image
node scripts/audit-native.mjs --mode video
node scripts/audit-native.mjs --mode frame --asset "<exact image title>"
node scripts/audit-native.mjs --mode last-frame --asset "<exact image title>"
node scripts/audit-native.mjs --mode frame-pair --asset "<first image title>" --asset "<last image title>"
node scripts/audit-native.mjs --mode reference --asset "<image title>" [--asset "<second image title>"]
node scripts/audit-native.mjs --mode video-reference --asset "<video title>" # blocked until the V2 config/bridge dependency is implemented
node scripts/audit-native.mjs --mode edit --asset "<exact video title>"
node scripts/audit-native.mjs --mode continue-exact --asset "<exact video title>"
node scripts/audit-native.mjs --mode continue-likeness --asset "<exact video title>" --character-name "<exact character name>"
node scripts/audit-native.mjs --mode agent
node scripts/audit-native.mjs --mode reangle --asset "<exact image title>"
node scripts/audit-native.mjs --mode character --asset "<exact image title>" --character-name "MCP E2E Character"
node scripts/audit-native.mjs --mode character-edit --character-name "<existing exact name>" --rename-character "<new unique name>"
node scripts/audit-native.mjs --mode upload --file "C:\path\to\reference.png"
```

Use an asset already listed by `--mode readonly`; the runner verifies the exact title and required image/video kind before submitting. Repeat `--asset` for multiple image references or the first and last frame pair. Continue-likeness requires a listed character; continue modes keep the existing similar-recent-asset guard unless `--force-continue` is explicitly supplied after checking Flow. Upload requires an explicit local file. Reports use unique timestamped filenames so prior diagnostics are preserved. To select another local port, set `$env:FLOW_LOCAL_API_BASE = 'http://127.0.0.1:<port>'`; the runner rejects non-loopback addresses.

### Source parity notes

- Toby `FlowApiAdapter.js::_computeVideoGenType` maps text, first-frame, first/last-frame, image-reference video, and video-edit inputs to distinct generation types. Local API supports text video, first/last frames, frame pair, and image references. Its `video_reference` shape accepts a video asset title but fails closed before queueing, so native does not yet submit a video asset as a generation reference. Local `flow_edit` is a separate edit workflow and should not be conflated with Toby's video-reference generation type.
- The local `video_reference` input is only a validated API shape and fails closed before queueing with `FLOW_VIDEO_REFERENCE_CONFIG_UNAVAILABLE`. Toby's implementation gets `flow_api_v2_protocol`, `models`, `schema`, `state_mapping`, `runtime`, and `error_mapping` from protected private provider config (`ProviderConfigManager.fetchFlowApiV2Configs` → protected `extension-config/providers/private-configs`); the video route specifically needs `models.video_edit_video`, `protocol.rpc.video_edit_submit`, and configured `video_edit_frames`. Submission also uses Toby's separate V2 bridge extension (`flow_v2_submit_video_edit`). Native has neither the protected-config/device-auth client nor that bridge. The route remains **unsupported/incomplete** until an authorized config-and-bridge contract is available or protected backend integration is implemented. Do not treat schema/parser tests or the blocked audit mode as live evidence.
- Toby's standalone upscale path is distinct from ordinary media download: `EditorExecutor` selects it when the requested resolution route is `upscale`, then calls `FlowApiFacade.upscaleImage` or `upscaleVideo` with the media ID, project ID, and requested resolution. V2 calls require protected V2 config and bridge methods `flow_v2_upscale_image` / `flow_v2_upscale_video`; video additionally validates an `_upsampled` media receipt and polls/resolves that output. Native already supports a UI-based high-quality download through `flow_download`/`flow.asset.download` with `quality: "upscaled"` (the visible menu is matched for image upscaled/2K and video 1080p), but it does not expose Toby's standalone resolution-selectable API upscale or 4K route. No separate native route is added without the authorized config/bridge contract; high-quality download is not evidence of standalone upscale parity. No live upscale E2E is recorded.
- Minimum authorized V2 contract for `video_reference`: a versioned protected-config response for the six Toby config sections (`protocol`, `models`, `schema`, `state_mapping`, `runtime`, `error_mapping`) obtained through the authenticated private-config path; it must contain the `video_edit_video` model mapping, `protocol.rpc.video_edit_submit`, video aspect-ratio schema, valid configured `video_edit_frames`, and the needed resolution/reference mapping.
